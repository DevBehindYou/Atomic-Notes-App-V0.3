# Automatic images: 60 KB quality update

The owner's latest request supersedes the earlier 24 KB cap. New gallery images
are automatically optimized to **at most 60,000 raw JPEG bytes each**, with no
quality/settings or insertion confirmation. The three-image insertion cap stays.
Existing saved images are never recompressed; a better-quality original must be
selected again to recover detail already removed by an older compression pass.

## Compression

The native gallery request uses quality 100 instead of discarding detail at
quality 70 before the optimizer runs. The background optimizer tries JPEG quality
85, 75, 65, 50 and 40 at each existing bounded dimension, accepting the first
candidate that fits the smaller of 60,000 bytes and remaining aggregate space.
The 1024-pixel output bound, 8 MiB source allowance, four-megapixel decode bound,
no-upscale rule, aspect ratio, white transparency composite and metadata removal
remain. Input support remains JPEG/PNG through the existing pipeline.

## Matched app/server bounds

Three images can use 180,000 raw bytes, approximately 240,000 characters once
base64-embedded in the rich document. Real AES-GCM encryption adds a nonce/tag
and another base64 layer, producing roughly 320,000 payload characters before
other content. Raising only the per-image cap would leave the previous aggregate
and server limits rejecting these notes.

| Bound | Current limit |
| --- | ---: |
| New image | 60,000 raw JPEG bytes |
| Image additions | 3 per note |
| Aggregate images | 180,000 raw bytes |
| Body | 262,144 UTF-16 units |
| Encrypted payload | 393,216 base64 characters |
| Complete parsed row | 400,000 UTF-8 JSON bytes |

Both plaintext and projected encrypted content must fit before insertion/save.
The legacy per-image decoder retains its previous 61,440-byte allowance. The
2,500,000-byte/50-row push envelope, 4 MiB server request cap and ten-row pull
page remain unchanged; repository push batching already accounts for byte size.
The per-row wire allowance also keeps ten valid API rows within the hosting
response allowance without increasing page size.

## Rollout and parallel ownership

1. Merge and deploy the matching Server bounds before releasing this client.
   Older servers reject larger new notes; retain the local dirty draft and
   resolve the server compatibility dependency before production acceptance.
2. Pin App CI's actual Server fixture to the reviewed Server revision, verifying
   that its source tree matches the accepted Server merge before App merge.
   Verify actual HTTP plaintext and encrypted three-image roundtrips and
   oversized-note rejection, in addition to local crypto/Hive tests.
3. Merge the independent removal-confirmation change. Removing an image asks
   Keep image / Remove image; only Done persists draft changes.
4. Build an exact-source Android acceptance APK in Actions, verify its assets,
   package and signer, and preserve a fresh current device snapshot before any
   approved test-app replacement. Never restore an older note or mascot choice.

The quality work owns the adapter, insertion budgets, model/persistence/editor
regressions and this document. The Server work owns shared wire limits and their
boundary/HTTP tests. The removal work owns only the popup and stable row identity.
Preview, encryption algorithms, permissions and production deployment are unchanged.

## Verification

Regressions cover the 60,000/60,001-byte insertion boundary; improved decoded
fidelity versus a 23,999-byte budget; three full-size images through storage,
actual AES-GCM and sync projections; aggregate/body/payload/wire rejection;
legacy-byte preservation; metadata stripping; and failure without draft loss.
Required CI and physical device checks are separate gates. Do not describe a
source test as physical pinch, real OAuth/Drive, iOS or performance acceptance.
