# Mascot acceptance sequence — bundled delivery

Current source checks: all 52 original sizes/digests and native GIF frame counts/cycle durations passed; fatal-info analysis clean; full local suite 780 passed, 33 platform-specific skips. These results do not establish device, store, browser, or photosensitive-motion acceptance.

Use a disposable install/profile and synthetic notes. Record app commit, version, build flavor, OS/device/browser, text scale, accessibility settings, network state and timestamps. Do not use personal account data in captures. Keep implementation evidence separate from release acceptance.

1. Start a fresh Android install offline. Open notes immediately, enter Settings > Mascot, select each of the 13 supplied characters, and verify four variations without network access. Relaunch and confirm the favorite and motion preference persist. Reinstall/clear-data is destructive: use only the disposable test install.
2. Touch the Home character repeatedly and use keyboard/assistive activation where supported. Confirm variation changes within the same character and that the same activation shows live sync information. Confirm no adjacent reload/status icon, no duplicate boundary variation, no note edit, no sync request and no Energy charge. Verify idle/pending/error/success messages, live updates, second-tap dismissal, three-second auto-hide and cleanup after navigation.
3. Turn animation off and enable system reduced motion separately. Confirm still artwork, deliberate touch changes, no background animation, and usable navigation at 320px with 200-percent text. Explore names, selected state, motion switch and status with TalkBack; verify targets at least 48dp, visible focus, keyboard Enter/Space and readable contrast.
4. Cycle Home, Settings, pushed routes, lock/unlock and background/resume at least twenty times. Confirm one visible animation, hidden routes stop, no crash or leaked decoder, and notes/auth state unchanged. Repeat rapid favorite changes while preferences are loading/saving. Future preference schemas must remain intact and read-only.
5. Review all 52 full animations in light and dark surrounding UI, first and last frames, crops, and transitions. Review flashing/motion sensitivity with appropriate tooling and qualified human judgment. Do not infer a photosensitivity pass from GIF metadata. The artwork is decorative; depictions of locks/rewards/retry/save must never claim actual account or note operations.
6. Compare a fixed five-minute notes sequence with mascot motion on and off on a representative low-end and current Android device. Record startup latency, frame-time p50/p95/p99, dropped frames, CPU/GPU, memory before/after twenty navigation cycles, encoded cache and battery/thermal behavior. Record APK/AAB and delivered sizes. Use the reviewed planning budgets as targets, not achieved results; native GIF buffers remain 480px.
7. Run account/sync sequences against the owner's isolated staging deployment only after its URLs are supplied. Include offline edits, reconnect, conflicts, recovery, background transitions and sign-out. Confirm mascot interactions never alter account boundaries or billing. No deployment green flag is issued here.
8. Browser testing begins only after the separate WebApp shell and platform adapters are accepted. Use bundled same-origin static assets, keyboard-first workflows, offline/reload behavior and target browser automation. Android compile feasibility does not certify the professional WebApp. iOS needs its own supported-device evidence.

Attach redacted logs/screenshots and a pass/fail per step. Any failed safety, data-isolation, accessibility or motion check blocks release; do not replace failed evidence with an average percentage. PR merge requires independent review, all required checks at the current head and no merge conflicts.
